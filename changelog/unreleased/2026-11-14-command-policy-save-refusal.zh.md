# 安全策略页的一次保存被拒时，说清仍在执行的是哪一份策略

- **日期:** 2026-11-14
- **类型:** 修复
- **范围:** `web`
- **破坏性变更:** 否

[English](2026-11-14-command-policy-save-refusal.md)

项目设置「安全策略」页的一次保存，整块 PUT `[command_policy]` —— 主开关与全部规则，所以被拒时屏幕上的控件
显示的是**引擎没有在跑**的那一份：刚关掉命令拦截的人以为下一条命令不会被挡，刚加了一条 deny 规则的人以为它
在生效。而那条拒绝只落在一句通知里，念的是错误自己的话，六秒后就自己消失，留下一张看起来已经保存的列表。
这正是全应用那条「被拒的原因留在发问的地方」的规则，而这一页是项目设置里最后一处还在发通知的写。

现在这句话画在保存按钮自己那一行里，并且说清项目仍在执行什么：主开关是这次尝试的一部分时，它点名仍在生效的
那一个状态（命令拦截仍是启用、或仍是停用，规则也还是上一次保存的）；只动了规则表时，它说存下来的策略没有被
动过，绝口不提开关变过。每次尝试先清掉上一次那句，保存按钮仍然是重试。

规则表是这一页唯一能悄悄撑破的东西：路由把一份策略限制在 64 条规则，而页面既不说明也不在此拦下 —— 这既是这条
拒绝能走到的地方，也是这句话的价值所在：第 65 条规则无声无息地没进文件，正是这一页过去留下的那种不解释的状态。

## 细节

- `packages/web/src/lib/command-policy-save-refusal.ts`（新增）：`commandPolicySaveRefused(attempt,
  error)` —— `{ enabled, savedEnabled }` 加上那句话，原因走 `refusalText`（服务端给的答案念它自己
  错误码的本地化句子，本仓库自己抛出的失败按它写的原样显示）。这次尝试随句子一起返回，调用方因此能分辨
  三种情形里的哪一种。
- `packages/web/src/components/layout/project-dialogs.tsx`：`SecurityPolicySection` 把这句话放进
  `saveRefusal` 槽，不再 `toastError`；每次尝试开始时先清掉上一次那句，切 Project 时一并清掉。句子是
  `role="alert"`（`data-testid="command-policy-refusal"`、最多两行、悬停看全文），画在保存按钮旁边 ——
  在按钮**那一行**里，而不是压在它上方：规则表本身就已经撑出这个对话框的滚动框，压在按钮上方的句子会把
  「重试」正好在需要它的时候推出视野。
- 词典（`strings.ts` / `strings-en.ts`）：三句 —— 开关仍是启用、开关仍是停用、存下来的策略没被动过。
- 没有接口变化、没有新依赖、服务端行为没变。

## 测试

- `packages/web/test/command-policy-save-refusal.test.ts`（新增，6 条）：被拒的「关掉」说拦截仍启用；
  被拒的「打开」说仍停用；开关没动时绝不声称它变过；映射过的错误码念界面的语言而不是线上那句话；无话可说的
  值落到通用文案；句子跟随当前词典。
- `packages/web/e2e/command-policy-save-refusal.spec.mjs`（新增，2 条，真服务端 + 真浏览器）：项目里已有
  64 条规则（路由的上限），草稿通过表单加进第 65 条 —— 同时把开关也关掉时，句子点名引擎的状态与服务器自己的
  原因，通知区 0 个按钮，存下来的策略仍是那 64 条，七秒后句子仍在；把表恢复到上限以内后按**同一个按钮**即落地。
  只动规则表的那一次不声称开关的任何状态，存下来的策略与之前读到的一模一样。

## 兼容性

线上协议没变：同一个 PUT、同一套校验。变的是被拒的一次保存告诉读者什么，以及它在发问的那个控件旁边告诉。
