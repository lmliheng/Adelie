# 分组密钥那张框被拒时留着，敲进去的密钥与原因也留着

- **Date:** 2026-11-23
- **Type:** fix
- **Scope:** `web`

[English](2026-11-23-group-key-refusal.md)

模型库每个分组表头上有一个「填写密钥」，一次把一把密钥写进这一组的全部模型。过去它按一下就关框，
写入随后才开始 —— 服务端拒绝时，原因只落在一条六秒就走的通知里，而那把刚敲进去的密钥已经跟着框一起
不见了，分组表头上也看不出刚按过什么。

现在只有真的写进去才关框：被拒时框站着，密钥还在字段里，服务端原话以「操作被拒绝：…」画在字段上方，
确认按钮就是重试。写入在途时取消与确认都灰着，框也不会被点外面关掉。

## 细节

- `packages/web/src/features/models/models-page.tsx`：`GroupKeyDialog` 自己拿 `busy` 与 `refusal`，
  `onSubmit` 改成返回「拒绝的原话，或写入成功的 `null`」；每次尝试开始先清掉上一次的句子，成功时由
  页面关框。句子走库里既有的 `NoticeStrip`（`role="alert"`、危险墨色，正文在 `data-slot="body"`），
  与工单那几张框同一套写法。
- 没有新文案、没有新依赖、不碰接口：写的仍是整表 PUT，只是关框挪到写入落地之后。

## 测试

- `packages/web/e2e/models-group-key-refusal.spec.mjs`（新，2 条，真服务端 + 仓库自带 mock 模型）：
  ①整表 PUT 被按 500 交回 → 句子在框里、框还开着、字段里仍是刚敲的密钥、通知区没有它、七秒后仍在、
  PUT 只发过一条且带上那把密钥；②解除拦截后按同一个确认 → 框关掉、通知说「已为 1 个模型配置 API key」、
  服务端该行的密钥确实存下了。
- `@adelie/web` 的 `tsc --noEmit` 与既有单测、`prettier --check`、`oxlint` 全过。

## 兼容性

没有动路由、存储格式或线上类型：这一处只改「什么时候关框、原因画在哪」。
