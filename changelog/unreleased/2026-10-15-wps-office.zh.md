# 能让 Adelie 读改你正在看的 WPS 文档了

- **Date:** 2026-10-15
- **Type:** feat
- **Scope:** `plugins`

[English](2026-10-15-wps-office.md)

新插件：**WPS**（`@adelie/use-wps-office`）。它把 Adelie 的对话搬进 WPS 文字——功能区点一下开侧栏，
再把你屏幕上那份打开的文档交到 Agent 手里：九个操作（读概况、读正文、搜索、替换、插入、删除、插分隔符、
新建、定位）以 `mcp__wps__*` 工具的形式交给会话。

运行时就是一个零依赖的 Node 文件（`kit/serve.mjs`），全程不出这台机器：桥只绑 `127.0.0.1`，Adelie 走
回环地址访问，不对网络开任何端口。桥只做四件事——托管加载项那页、把文档指令下发给真正执行它的面板、
替面板跟 Adelie 说话、通过 WPS 自己的本机上架服务（`127.0.0.1:58890`）登记加载项。之所以要有这个桥，
是因为面板跑在 WPS 的内嵌浏览器里、与 Adelie 不同源，而 Adelie 明确不开 CORS。

改文档要用户点头：面板建的会话是**只读**的，读随便读，每一处改动都是一次用户要在侧栏里回答的审批。
替换与删除都能带一个 `expect`（那一段现在的原文），对不上就拒绝执行并回「段落已变，先重新读取」——
模型读到的段号是会过期的。

指令一次只跑一条、按顺序，因为同一份文档上两个写者会让两边都读不懂；面板始终不回话时，那一轮会报一句
看得懂的错，而不是一直卡着。

安装脚本 `install.mjs` 会写设置、把加载项交给 WPS、把桥登记成 Agent 的一个 MCP 服务器并自己连一次核对、
在 Windows 的启动文件夹放一个开机自启项、然后把桥拉起来。每一步都可以重复跑，所以**重跑就是修复**；
`uninstall.mjs` 是它的反面。设置、状态和 `bridge.log` 都在 `<数据根>/wps-bridge/` 下，**不放插件目录**
（插件更新会整体替换）。

**没有验证到的：WPS 那一侧本身。** 面板和桥这边都测过（桥、安装脚本、加载项托管走 `node --test`；
十四条浏览器测试让真面板跑在假 WPS 上），但功能区的按钮、任务窗格、文档接口只在装了 WPS 的机器上存在，
第一次必须发生在 Windows 上、并且当着 WPS 的面。
