# 卸载技能被拒时，确认框留着，原因也留在框里

- **Date:** 2026-10-22
- **Type:** fix
- **Scope:** `web`
- **Breaking:** no

[English](2026-10-22-skill-uninstall-refusal.md)

智能体设置的「技能」页里，卸载一个技能要先确认，而那张卡片过去在 `finally` 里关掉 —— 不管答复是什么。被拒
的时候技能在页面上与磁盘上都还装着，可原因却是一条 toast：六秒，浮在卡片上方，而重试要自己再去把那一行找回来。

现在卡片在**卸载真的落地之后**才关：被拒的请求把服务端的原话画在句子下面，重试就是同一个按钮；卸载成功的那
一次才关框、清掉那句话，并重读一遍已装列表。从行上的「移除」打开卡片时先清掉上一次的原因。

## 细节

- 规则沿用模型库、定时任务、评估中心、插件市场、删除对话、插件设置与 MCP Server 那几轮（`ConfirmModal` 的
  `refusal` 槽）：原因画在发起它的那张卡片里，而不是一条会自己消失、还浮在框上方的 toast。
- `features/agents/skills-tab.tsx`：`confirmRemove` 在 `removeAgentSkill` 被拒时留住卡片，把原话交给新的
  `removeRefusal` 状态，由确认框画出来（`S.common.refused(...)`）；成功时才清掉待卸载的名字、弹成功提示、
  重读本页并刷新智能体列表。写入在飞时行上的按钮与卡片本来就标着 `busy`，所以不会被连点。
- 新增浏览器用例 `e2e/skill-uninstall-refusal.spec.mjs`（两条）：被拒的卸载留着卡片、句子与那个技能，不弹
  toast，重新打开时不带旧原因；被拒之后再确认一次、这次放行 —— 卡片关掉、行消失、服务器那份已装列表里也没有它。

## 兼容性

- 没有接口、传输格式、已存数据或依赖变化：只改了「框什么时候关」与「原因画在哪」。
- 同一页的导入流程把拒绝报在导入对话框里（`uploadError`），本来就把原因放在重试旁边，未动；钩子页那条同形的
  卸载流程也照旧，留给它自己一轮。
