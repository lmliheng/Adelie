# 删除 MCP Server 被拒时，确认框留着，原因也留在框里

- **Date:** 2026-10-22
- **Type:** fix
- **Scope:** `web`
- **Breaking:** no

[English](2026-10-22-mcp-delete-refusal.md)

智能体设置「工具」页的 MCP Server 表里，删除一行要先确认，而那张卡片过去在请求返回时就关掉 —— 不管写没写
成功。被拒的时候列表在页面上与服务器上都一点没变（「删除一行」就是把整张表去掉这一行再 PUT 回去），可原因
却是一条 toast：六秒，浮在卡片上方，而重试要自己再去把那一行找回来。

现在卡片在**写成功之后**才关：被拒的写入把服务端的原话画在句子下面，重试就是同一个按钮；写成功的那一次才关
框并清掉那句话。从行上的「删除」打开卡片时先清掉上一次的原因。

## 细节

- 规则沿用模型库、定时任务、评估中心、插件市场、删除对话与插件设置那几轮（`ConfirmModal` 的 `refusal` 槽）：
  原因画在发起它的那张卡片里，而不是一条会自己消失、还浮在框上方的 toast。
- `features/agents/mcp-servers-section.tsx`：`confirmDelete` 只在 `persist` 回真时 `setDeleting(null)`；
  被拒时把原话交给新的 `deleteRefusal` 状态，由确认框画出来（`S.common.refused(...)`）。写入在飞时确认框
  本来就标着 `busy`，所以两个按钮不会被连点。
- 新增浏览器用例 `e2e/mcp-delete-refusal.spec.mjs`（两条）：被拒的删除留着卡片、句子与那一行，不弹 toast，
  重新打开时不带旧原因；被拒之后再确认一次、这次放行 —— 卡片关掉、行消失、服务器那份列表里也没有它。

## 兼容性

- 没有接口、传输格式、已存数据或依赖变化：只改了「框什么时候关」与「原因画在哪」。
- 同一个区块里新增 / 编辑的对话框本来就自己留着服务端的 400（`modalError`）、开关那条没有框可留，两者都没动。
