# 两张凭据表的删除确认框：被拒时框留着，原因也留在框里

- **Date:** 2026-10-23
- **Type:** fix
- **Scope:** `web`
- **Breaking:** no

[English](2026-10-23-vault-delete-refusal.md)

两张凭据表 —— 智能体自己的密钥（智能体设置 › 密钥保险柜）与账户的全局密钥（账户菜单的「用户密钥」）—— 删除
一行都是把整张表去掉那一行整表写回去。两张确认框过去都在写入返回后无条件关：被拒的时候，那把密钥还在页面上、
也还在服务端，原因却只落在一条六秒后自己消失、还浮在框上方的 toast 里。

现在两张框都只在**写入真的落地之后**才关；被拒时框留着，服务端的原话画在框里（在它自己那句话下面），重试就是
同一个按钮。

## 细节

- 规则沿用模型库、插件卡、技能 / 钩子 / MCP 页、删除对话、定时任务页与两张批量更新确认框那几轮（`ConfirmModal`
  的 `refusal` 槽，7.19—7.30）：原因画在发起它的那张卡片里。
- `features/agents/vault-tab.tsx` 与 `components/account/user-vault-dialog.tsx`：`confirmRemove` 不再把错误
  弹成 toast 然后关框，而是把消息交给 `deleteRefusal` 状态、由确认框用应用自己的「操作被拒绝：」前缀
  （`S.common.refused`）画出来；`setDeleting(null)` 只在写入落地时执行。
- 取消之后重新打开，先清掉上一次的原因：那句话属于上次尝试点名的那把密钥。
- 被拒的「添加」不变：错误落在产生它的表单上，那张表单就在确认框下面开着。
- 新增浏览器用例 `e2e/vault-delete-refusal.spec.mjs`（两条：智能体的表与账户的表）：被拒时框、句子与密钥都在，
  通知区没有 toast，重新打开不带旧原因；只有放行重试的那次才关框，而它发出的写入正是去掉那一行的表。两处的初始
  数据与拒绝都由接口 / `page.route` 造，验的就是页面与服务器之间的契约。

## 兼容性

- 没有接口、传输格式、已存数据或依赖变化：只改了「框什么时候关」与「原因画在哪」。除既有的
  `S.common.refused` 前缀外没有新文案。
