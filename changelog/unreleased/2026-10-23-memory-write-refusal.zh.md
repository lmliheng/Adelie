# 记忆页签：删除与导入被拒时，框留着、原因也留在框里

- **Date:** 2026-10-23
- **Type:** fix
- **Scope:** `web`
- **Breaking:** no

[English](2026-10-23-memory-write-refusal.md)

智能体设置 › 记忆里的两条写入都会先问一句：删掉一条记忆，或者把一份记忆导出文档导回某一组。过去两句问法都
在请求返回后自己关掉：被拒的时候，那条记忆（以及导入要覆盖的文件）还在页面上、也还在磁盘上，原因却只落在一条
六秒后自己消失、还浮在弹框上方的 toast 里 —— 删除框甚至在发请求之前就先关掉了。

现在两条写入都只在**真的落地之后**才收框：被拒时删除确认框留着，服务端的原话画在它那句话下面；导入则把原话画在
发起它的那一层 —— 走过计划确认的落在计划确认里，不需要确认的那条落在下面那层「导入记忆」里。重试都是同一个按钮。

## 细节

- 规则沿用模型库、插件卡、技能 / 钩子 / MCP / 密钥保险柜 / 定时任务页与两张批量更新确认框那几轮（`ConfirmModal`
  的 `refusal` 槽，7.19—7.31）：原因画在发起它的那张卡片里。
- `features/agents/memory-tab.tsx`：`confirmRemove` 不再先 `setRemoving(null)`，被拒时把消息交给
  `deleteRefusal` 并提前返回；只有删除真的写下才关框、刷新列表并重载智能体卡片上的条数。行的垃圾桶、抽屉与
  手机面板底部的删除都走同一个 `askRemove`，它先开框再清上一次的原因 —— 那句话属于上次点名的记忆。
- `runImport` 失败时不再弹 toast，而是把消息交给 `importRefusal`；成功路径不变。原因的画法按「哪一层在问」分：
  计划确认（`ConfirmModal`）画在它自己的 `refusal` 槽，没走确认的直接导入画在导入弹框里（`S.common.refused`
  前缀两边一致）。取消计划确认回到导入弹框时，那句话仍然看得见；重新挑文件或换一种模式即清掉。
- 新增浏览器用例 `e2e/memory-write-refusal.spec.mjs`（三条）：删除被拒时框、句子与记忆都在（通知区没有 toast，
  框里的文字除那一行外逐字不变），取消不改变任何东西；放行重试才关框，且它发出的正是那条 DELETE；导入被拒时
  计划确认留着、原话在里面，那一组在磁盘上与页面上都还是导入前的样子，只有放行重试才写下去。初始的记忆文件由
  导入接口自己种下（这个页签按设计没有「新建文件」表单），两处拒绝都由 `page.route` 造，验的是页面与服务器之间
  的契约。

## 兼容性

- 没有接口、传输格式、已存数据或依赖变化：只改了「框什么时候收」与「原因画在哪」。除既有的
  `S.common.refused` 前缀外没有新文案。
