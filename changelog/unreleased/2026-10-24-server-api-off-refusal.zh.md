# 智能体 API：全服务器的关闭开关被拒时，框留着，原因也留在框里

- **Date:** 2026-10-24
- **Type:** fix
- **Scope:** `web`
- **Breaking:** no

[English](2026-10-24-server-api-off-refusal.md)

设置 › 服务器 › Agent API 上那个开关是管理员的：关掉之后，所有 Agent 的 API 请求一律被拒。关闭它会先问一句
（危险色）。这句问话过去在按下确认的那一刻就自己关掉、然后再发请求，于是写入被拒的时候，原因落在**框已经离开
的**那个开关下面 —— 想重试得重新打开这张框，而那句说明读起来像是页面级的一条消息，而不是这次提问的一部分。

现在框留到自己的写入落地；被拒时框留着，服务端的原话画在它自己那句话下面（`ConfirmModal` 的 `refusal` 槽，
用的是应用既有的「操作被拒绝：」前缀），重试就是同一个按钮。写入在途时框上两个按钮置灰；重开这张框会先清掉
上一次的原因 —— 那句话属于上次那次尝试。

## 细节

- `features/settings/agent-api-section.tsx`：`AgentApiServerOffConfirm` 不再在写之前调 `onClose()`，而是把
  结果交回去，由这一页只在写入落地时才关框（`settleOff`）。被拒时把 `offRefusal` 画进框里（经
  `S.common.refused`），开关回到服务端仍然持有的那个值。框新增 `busy`（写入在途时两个按钮置灰）与 `refusal`
  两个 prop；开关自己那个入口在打开框时先清掉上一次的原因。
- **打开**开关没有自己的框，仍按原来的方式报：写入被拒就把开关放回存储值、在它下面说明原因。
- 新增浏览器用例 `e2e/server-api-off-refusal.spec.mjs`：用 `page.route` 把写入拒成 500 之后，框、框里那句话
  与服务端的 `agentApiEnabled: true` 都不变（通知区没有可点的按钮），重开不带旧原因；在同一张框上重试才真正
  写入 —— 框关、开关翻到 false、服务端回 `false`。用例结束时把开关留在打开状态，其他用例是在它打开的前提下
  调用各 Agent 的 API 的。

## 兼容性

- 没有接口、传输格式、已存数据或依赖变化：只改了「框什么时候关」「原因画在哪」，以及写入在途时框上的按钮
  置灰。除既有的 `S.common.refused` 前缀外没有新文案。
