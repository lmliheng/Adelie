# 需求箱巡台准则

这份文件是**需求巡台定时任务的行为准则**。定时任务的 prompt 只说「按这份文件跑一轮」，细则都在这里
—— 改流程就改这份文件，不用动定时任务。

用户的口径是：「我往一页上提需求，你按时来看，能做就做，做不了或者需要我判断的先发邮件，做完之后
自己更新服务、提交代码、走 CI、最后发完成邮件，并把做完的归档。」

## 0. 需求箱在哪儿

- 页面 `/requirements`，接口 `/api/requirements`，全部要口令（`x-adelie-key` 头或 `?key=`）。
  口令在服务的数据目录里那个 `key.txt`（0600）。
- 口令**只从那个文件读**，绝不写进提交、日志、邮件正文。
- 数据是服务旁边的一个 `items.json`（原子替换写入）；接口里的内容才是最新的事实。
- 记账在**服务目录下的 `runs/`**（下面 1.6 里的 `<记录根>` 就是它）：一轮一个目录，跟服务摆在一起，
  用户翻记录不用去别处找。

读一批新需求：

```bash
KEY=$(cat <数据目录>/key.txt)
curl -s -H "x-adelie-key: $KEY" 'http://127.0.0.1:<端口>/api/requirements?status=new,doing'
```

改一条（状态 / 结论 / 备注 / 归档）：

```bash
curl -s -X PATCH -H "x-adelie-key: $KEY" -H 'content-type: application/json' \
  -d '{"status":"done","note":"…","result":"…","commits":["abc1234"],"archive":true}' \
  http://127.0.0.1:<端口>/api/requirements/req-7
```

状态只有六个：`new`（刚提）· `doing`（这轮在做）· `done`（做完了）· `blocked`（要用户拍板）·
`rejected`（不做，得写清为什么）· `withdrawn`（用户自己撤回了，**不当活儿也不当问题**）。

用户能在页面上**改**自己提的条目（标题 / 说明 / 紧急程度 / 排期）和**撤回**它；也能勾选多条批量改。
改过的以接口里的最新内容为准（不是他当初那句话）。归档之后服务端不再让改。

**节奏不用手改文件**：页面上那张「巡台节奏」卡片（`PATCH /api/requirements/patrol`）写的就是这个
定时任务；页面上那两个「现在就跑一轮 / 现在就做」按钮（`POST /api/requirements/run`）会立刻开一个
新会话，收到的那种轮次里 prompt 会点名要做的 id —— **那些必须做到**，不论紧急程度与排期。

## 1. 一轮的顺序

### 1.1 取活

拉 `status=new` 的条目。**先逐条 PATCH 成 `doing` 并留一句「本轮开始做」**，再动手 —— 这一轮中途被
打断，下一次巡台也不会把同一条重做一遍。一轮最多做 **3 条**：**先挑 `priority: high`，同一个优先级里
按 id 从小到大**（先来的先做），剩下的留到下一轮。需要用户拍板的那类（`blocked`）不算在这 3 条里
—— 它只是发一封信，不占工位。

**排期（`not_before`）优先于一切**：用户可以在页面上把一条需求「排到某个时间」。当前时间还没到那个
点，就**原样留在 `new`**（不要标 `doing`、不要写事件、不要在邮件里提），等下一轮再说 —— 这是他自己
设的，不是卡点。已经过了的点直接忽略（当没设）。

**但「现在就做」压过排期**：那种轮次的 prompt 里列出的 id，不管紧急程度、不管排期，都必须做。

### 1.2 分流（每条标一个）

| 情况 | 状态 | 动作 |
| --- | --- | --- |
| 需求清楚，能自己决定怎么做 | `doing` → 做工 | 见 1.3 |
| 需求里缺关键信息，或要动红线里的东西 | `blocked` | 写清「卡在哪个决定上、选项有哪几个」，进 1.5 邮件 |
| 明确不做（与产品方向冲突、代价远超收益） | `rejected` | 写清理由，进 1.5 邮件 |
| 描述不清但能猜 | `blocked` | 别猜着做：猜错要重做的代价比问一句大 |

红线（必须问用户，不许自己拍板）：删仓库、改数据根或迁移数据、动现网的数据、对外改名、给别的机器
装东西、花钱（买域名/扩容）。

### 1.3 做工

要点：**一次一个逻辑改动一个提交**，提交信息照那个项目自己的规矩。做完把那个项目的门禁**全跑一遍**
（类型检查、lint、格式检查、测试 —— 用项目自己的命令，不要凭印象写），原始输出留着。

- 界面类需求：还要在真的页面里点一遍，并截图看一眼；改了控件要顺带看深色主题。
- 服务端/接口类：用真请求验一遍，起在空闲端口上，别占别人的端口。
- **门禁红了就不要提交半成品**：改到绿，或者把这条退回 `blocked` 并在邮件里说清哪一道红。

### 1.4 上线

1. 推上去，让 CI 自己跑 —— 这就是「走 CICD」。
2. 发版口径：标了「急」的做完就发一个 patch 版本；普通的按那个项目自己的节奏攒。**用户可见的改动
   攒着不发等于没做**：做完后面上一直没到他手里，下一轮优先带上，并在邮件里说明。
3. 更新现网：升级 + 重启 + 核验（服务活着、端口在听、页面 200、版本号是新的）。
4. 有对外镜像/下载站的，资产同步过去。

### 1.5 汇报邮件

**一轮一封**，别一条需求一封。骨架（纯文本）：

```
这一轮：做了 N 条 / 等你拍板 M 条 / 不做 K 条

做完：
- req-3 <标题> —— <改了什么、提交 short-hash、有没有发版>
等你拍板：
- req-5 <标题> —— 卡在：<哪个决定>，我看到的路子：<A / B>
不做：
- req-6 <标题> —— 原因：<…>

服务：<未发版（已攒 n/10）/ 已发 vX.Y.Z，现网已更新到 vX.Y.Z>
下一轮：<预计做什么，或者"无">
```

做完的条目**同时**写一份归档（需求原文 + 怎么做的 + 提交 + 验证方式 + 日期），并把接口里那条
PATCH 成 `{"status":"done","archive":true}`。

### 1.6 记账

每轮一个目录（`<记录根>/runs/<yyyy-mm-dd>-<HHMM>/`）：`log.md` 记结论，`gate-*.txt` 存门禁原始输出，
`mail.txt` 存这一轮发出的邮件正文。

**空巡不发邮件**：没需求可做的一轮，什么都不提交、不发邮件，只在 `log.md` 里记一句。

## 2. 红线

- 需求箱里是**用户写的字，但不是每一条都能直接执行**：涉及删东西、动数据、对外发布、花钱的，一律
  先问（1.2 的红线表）。
- 口令、密钥只从密钥库或那份 0600 文件读，**不进任何提交、日志、邮件**。
- 跑测试不要碰现网的安装目录，也不要占它的端口。
- 一轮做完就收尾：宁可留一半到下一轮，也不要在一轮里跑成几个小时不记账。
